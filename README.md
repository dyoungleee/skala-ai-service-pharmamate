# PharmaMate

> **제약·바이오 기사를 읽고, 이해하고, 질문하며, 학습 기록으로 축적하는 개인화 AI 학습 Agent**

- **작성자:** 광주캠퍼스 이다영
- **과제 유형:** 신규 AI Agent 개발(2번). (기존 자체 프로젝트 PharmaMate 2.2를 개선 전 기준선으로 활용)
- **기준선:** PharmaMate 2.2 (`PharmaMate_2_0.ipynb`, Jupyter Notebook + Gradio)
- **현재 구현:** PharmaMate 3.0 (Vue 3 + FastAPI + LangGraph + SQLite)

PharmaMate는 제약·바이오 분야 입문자가 뉴스 기사에 등장하는 전문 용어와 산업 이슈를 이해하도록 돕는 학습 서비스입니다. 기사 URL 또는 본문을 입력하면 핵심 내용을 정리하고, 기사 맥락에 맞는 용어 설명과 AI Tutor 질의응답을 제공합니다. 학습한 내용은 저장·검색·복습할 수 있으며, 이전 학습 이력과 직전 대화를 반영한 후속 질문을 추천합니다.

**학습 흐름:** 기사 입력 → 기사 브리핑·용어 탐색 → AI Tutor 질문 → 후속 질문으로 심화 학습 → 학습 메모 저장·복습

## 1. 프로젝트명 및 주제 선정 배경

### 프로젝트명

**PharmaMate — 제약·바이오 기사 기반 개인화 AI 학습 Agent**

### 주제 선정 배경

제약·바이오 기사에는 임상시험 단계, 약물 작용기전, 허가 절차, 기업의 개발 전략처럼 사전 지식이 필요한 개념이 빈번하게 등장합니다. 기사를 읽다가 전문 용어를 따로 검색하고, 다시 기사로 돌아와 맥락을 연결해야 하는 과정은 입문자에게 부담이 됩니다.

PharmaMate는 이러한 학습 과정을 하나의 서비스 안에 통합하기 위해 시작했습니다. 초기 2.2 버전에서는 Gradio 기반 기사 분석·질의응답·SQLite 학습 기록을 구현했고, 3.0에서는 **개인화 검색, 근거 검증, 동적 질문 추천, 웹 서비스 구조, 세션 복원**을 강화했습니다.

## 2. 해결하고자 하는 문제

- **기사 이해의 높은 진입 장벽:** 제약·바이오 기사에는 임상시험, 신약 개발, 약물 작용기전, 규제·허가 등 전문 용어와 배경지식이 빈번하게 등장합니다. 입문자는 핵심 내용과 산업적 의미를 파악하기 어렵습니다.
- **용어와 기사 맥락의 단절:** 모르는 용어를 별도로 검색하는 과정에서 기사 읽기의 흐름이 끊기고, 일반적인 정의를 찾아도 해당 용어가 _이 기사에서_ 왜 중요한지 이해하기 어렵습니다.
- **개인별 학습 수준과 후속 학습 방향의 차이:** 사용자마다 배경지식과 궁금한 내용이 다르지만 일률적인 요약은 이를 반영하기 어렵습니다. 기사 이해 이후 무엇을 더 질문하고 어떤 개념으로 확장해야 할지도 판단하기 어렵습니다.
- **과거 학습과 새로운 정보의 단절:** 이전에 공부한 약물·기술·임상 개념이 새로운 기사에 등장해도 기존 학습 내용과 연결하기 어려워 같은 내용을 반복해서 검색하거나 학습하게 됩니다.
- **학습 이력 관리와 복습의 어려움:** 읽은 기사, 학습한 용어, 질문과 답변, 개인 메모가 분산되면 학습 내용을 체계적으로 확인하고 복습하기 어렵습니다. 지식이 누적되기보다 일회성 정보 소비로 끝나기 쉽습니다.
- **개별 기사 중심의 단편적인 산업 이해:** 동일한 기업·신약·임상시험에 관한 후속 보도가 이어져도 기사 간 관계를 직접 정리해야 하므로 개별 사건을 산업 이슈의 흐름으로 연결해 이해하기 어렵습니다.

PharmaMate는 이러한 문제를 해결하기 위해 **기사 이해 → 맥락 기반 질의응답 → 후속 학습 → 학습 기록 축적·복습**을 하나의 서비스로 연결하고, 사용자가 제약·바이오 지식을 지속적으로 쌓을 수 있는 개인화 학습 환경을 제공하고자 합니다.

## 3. 개발 환경 및 기술 스택

PharmaMate는 **Vue 3 기반 프런트엔드와 FastAPI 기반 백엔드**를 중심으로 구성되며, LangGraph를 활용해 AI Agent의 질문 처리 흐름을 관리합니다. 사용자 학습 데이터는 SQLite에 저장하고, OpenAI 모델을 활용해 기사 분석, 질의응답 및 개인화된 학습을 지원하고 있습니다.

| 영역           | 사용 기술                     | 역할                                                     |
| -------------- | ----------------------------- | -------------------------------------------------------- |
| 개발 언어      | Python 3.11, JavaScript       | 백엔드 AI 로직 및 프런트엔드 구현                        |
| 프런트엔드     | Vue 3, Vite 6                 | 기사 분석, AI Tutor, 학습 기록 등 사용자 인터페이스 구현 |
| 백엔드 API     | FastAPI, Pydantic, Uvicorn    | REST API 제공, 요청·응답 데이터 검증 및 SSE 스트리밍     |
| AI Agent       | LangGraph, LangChain          | 질문 라우팅, 학습 기록 검색, 답변 생성 및 검증 흐름 관리 |
| LLM            | OpenAI GPT-4o-mini            | 기사 요약, 핵심 용어 분석, 질의응답 및 답변 검증         |
| 임베딩         | OpenAI text-embedding-3-small | 학습 기록의 의미 기반 검색을 위한 벡터 생성              |
| 데이터베이스   | SQLite                        | 사용자 세션, 학습 용어, Q&A 및 기사 학습 기록 저장       |
| 외부 정보 검색 | Tavily API                    | 최신 제약·바이오 정보 검색 및 답변 근거 확보             |
| 도구 연동      | MCP (Model Context Protocol)  | 외부 도구와 AI Agent 간 연동 인터페이스 제공             |
| 실시간 응답    | Server-Sent Events (SSE)      | AI Agent의 처리 단계 및 검증 완료된 답변을 실시간 전달   |
| 컨테이너 실행  | Docker, Docker Compose        | 웹 화면·API 실행 및 SQLite 데이터 볼륨 보존              |

### 기술 구성의 특징

- **프런트엔드와 백엔드 분리:** Vue와 FastAPI를 통해 사용자 인터페이스와 AI 처리 로직의 역할을 구분하고, REST API로 연결한다.
- **LangGraph 기반 Agent:** 질문의 특성에 따라 기사 맥락, 개인 학습 기록, 외부 웹 검색을 활용하는 처리 흐름을 구성한다.
- **SQLite 기반 개인화 학습:** 별도의 데이터베이스 서버 없이 학습 이력을 저장하며, 키워드 검색과 임베딩 유사도 검색을 결합해 과거 학습 내용을 재활용한다.
- **근거 기반 답변 검증:** 생성된 답변을 검증한 뒤 사용자에게 전달하여, 근거가 부족한 정보의 무분별한 제공을 줄인다.
- **SSE 기반 진행 상태 전달:** 질문 처리 단계와 최종 답변을 순차적으로 전달하여 사용자가 AI Agent의 진행 상황을 확인할 수 있도록 한다.

기술 선택의 세부 근거는 [`docs/adr/`](docs/adr/)에서 확인할 수 있습니다.

## 4. 시스템 아키텍처

```mermaid
flowchart TD
    USER[사용자] --> VUE[Vue 3 / Vite]
    VUE -->|REST / SSE| API[FastAPI]
    API --> ARTICLE[기사 URL·본문 추출 및 분석]
    API --> SESSION[세션·기사·메모 관리]
    API --> GRAPH[LangGraph AI Tutor]
    SESSION <--> SQL[(SQLite)]
    GRAPH --> ROUTER{질문 라우팅}
    ROUTER --> CTX[현재 기사 맥락]
    ROUTER --> RAG[개인화 혼합 검색]
    ROUTER --> WEB[선택적 Tavily 검색]
    RAG <--> SQL
    CTX --> ANSWER[LLM 답변 생성]
    RAG --> ANSWER
    WEB --> ANSWER
    ANSWER --> VALIDATOR{근거 검증}
    VALIDATOR -->|수정 필요: 최대 1회| ANSWER
    VALIDATOR -->|통과·근거 부족 처리| FOLLOWUP[후속 질문 추천·출처 정리]
    FOLLOWUP --> API
    MCP[MCP 읽기 전용 서버] --> SQL
```

### 핵심 처리 흐름

1. **기사 수집·정제:** URL 또는 붙여넣은 본문을 입력받아 기사 제목·부제목·본문을 분리하고 가능한 경우 캡션·관련 기사 등 주변 요소를 제거합니다.
2. **학습 컨텍스트 구성:** 기사 분석 결과와 선택 용어, 최근 대화, 저장된 학습 기록을 결합합니다.
3. **질문 라우팅:** LangGraph가 기사 문맥, 개인 기록, 최신 웹 검색 중 필요한 근거 경로를 선택합니다.
4. **검색 증강 답변:** 개인 기록은 임베딩·단어 혼합 검색으로 찾고 원본 기록 ID와 함께 답변 근거로 전달합니다.
5. **근거 검증:** Validator가 수치·날짜·임상 결과 등 주요 주장의 근거를 검사합니다. 필요하면 **최대 1회** 재작성하고, 여전히 확인할 수 없으면 근거 부족을 표시합니다.
6. **사용자 응답:** FastAPI가 SSE로 진행 상태·검증 완료 답변·출처·후속 질문을 전달합니다. **모델이 생성하는 토큰을 검증 전에 그대로 실시간 공개하는 구조는 아닙니다.**
7. **학습 저장:** 사용자 검토 후 메모·Q&A를 SQLite에 저장하고 세션 재방문 시 복원합니다.

## 5. 사용한 기술 요소 및 구현 결과

기능별 소개는 **목표 → 구현 → 검증 → 화면 캡처** 순서로 통일했습니다. 검증 수치는 각 실험 문서에 기록된 조건에 한정되며, 실제 사용자 환경의 품질이나 비용 절감을 보증하지 않습니다.

### 5.1 기사 입력·본문 정제 및 브리핑

**목표:** 기사에서 실제 본문을 읽기 쉽게 분리하고, 학습에 필요한 맥락을 함께 제공합니다.

**구현:** URL 또는 직접 입력한 본문에서 제목·부제목·본문을 구분합니다. 이미지 캡션, 페이지 메뉴, 관련 기사 등 본문이 아닌 요소를 제거하고 본문 문단은 유지합니다. 브리핑에는 기사 유형, 한 줄 정리, 업계 이슈, 주요 기업·기술을 표시합니다. 본문에서 같은 용어가 반복되면 처음 나온 위치만 강조하고, 사용자가 용어를 추가·제외할 수 있습니다.

**검증:** 본문 경계와 부제목 분리 사례를 실험 문서에 기록했습니다. 사이트별 HTML 구조, 유료벽, 동적 페이지에 따라 추출에 실패할 수 있으며 직접 입력을 대체 경로로 제공합니다. [본문 경계 실험](docs/experiments/F9_17_article_body_boundary.md), [부제목 분리 실험](docs/experiments/F9_15_article_subtitle_separation.md).

### 5.2 AI Tutor와 질문 경로 선택(Query Routing)

**목표:** 용어 학습과 기사 전체 질문을 지원하면서 질문에 맞는 근거를 선택합니다.

**구현:** 용어별 Quick Study를 `한 줄 정의 → 쉽게 말하면 → 이 기사에서는 → 지금 기억할 한 가지` 형식으로 제공합니다. 용어 질문은 기사와 선택 용어를, 일반 질문은 기사 전체 맥락을 사용합니다. 질문 유형에 따라 `article`, `memory`, `web`, `memory_web` 경로를 선택하며, 기사·학습 기록·최신 웹 근거를 구분해 답변과 참고자료를 제공합니다.

**검증:** 라우팅 합성 질문 24개에서 기존 설정은 23/24, 개선 설정은 24/24를 맞혔습니다. p50은 `1,152ms → 1,046ms`였고 토큰 사용은 소폭 증가했습니다. 따라서 이 평가에서 비용 절감은 확인되지 않았습니다. [Query Routing 평가](docs/experiments/F8_1_query_routing.md).

**화면 캡처:** 선택 용어의 Quick Study와 실제 Tutor 질문·답변이 함께 보이는 화면입니다.

### 5.3 LangGraph 역할별 처리와 동시 검색

**목표:** 질문 분석, 근거 검색, 답변 작성, 검증, 후속 질문 단계를 명확히 나누고 독립 검색의 대기 시간을 줄입니다.

**구현:** LangGraph 한 개의 그래프 안에서 라우터, 학습 기록·웹 검색, 답변 작성, Validator, 추천 질문 노드를 역할별로 연결합니다. 이는 여러 개의 독립 배포 Agent가 Supervisor 아래서 실행되는 구조가 아닙니다. `memory_web` 경로에서는 학습 기록과 웹 검색을 제한된 ThreadPoolExecutor에서 병렬 실행합니다(최대 8 worker). 별도 Dynamic Planner는 실험 결과에 따라 기본 흐름에 넣지 않았습니다.

**검증:** 고정 지연을 둔 합성 검색 30회에서 병렬 처리 p50은 `166.60ms → 84.60ms`, 성공은 30/30이었습니다. 실제 외부 검색 서비스와 모델 호출을 포함한 종단 간 지연은 측정하지 않았습니다. Planner는 12개 평가 질문의 경로 선택 개선 없이 p50이 `1,101ms → 2,036ms`, 모델 호출이 `12회 → 24회`, 토큰이 약 46% 증가해 채택하지 않았습니다. [병렬 검색 실험](docs/experiments/F8_4_parallel_sources.md), [Dynamic Planning 평가](docs/experiments/F8_2_dynamic_planning.md).

**화면 캡처:** 처리 단계는 서버 내부 흐름이므로 위 실험 기록을 검증 자료로 제시합니다.

### 5.4 개인화 RAG

**목표:** 현재 질문과 표현이 다른 과거 학습 메모도 찾아 답변 맥락에 활용합니다.

**구현:** SQLite에 저장된 학습 메모와 Q&A를 임베딩하고, 의미 유사도와 키워드 일치도를 결합해 검색합니다. 검색 결과는 원본 학습 기록으로 연결하며 임베딩 호출이 실패하면 키워드 검색으로 대체합니다.

**검증:** 합성 기록 14개와 질의 20개에서 Recall@3은 `0.950 → 1.000`, MRR은 `0.925 → 0.942`였습니다. 검색 p50은 약 `0.160초`로 늘었습니다. 검색 지표 향상이 최종 답변 정확도 향상을 뜻하지는 않습니다. [개인화 RAG 실험](docs/experiments/F2_personalized_rag.md).

**화면 캡처:** 이전에 저장한 용어·Q&A를 참고한 답변과 참고자료 목록입니다.

![Tutor가 저장된 학습 기록을 참고해 답변하고 출처를 표시한 화면](docs/experiments/assets/F5_4_personalized_rag_sources.png)

### 5.5 답변 품질 검증(Validator)

**목표:** 답변이 제공된 근거보다 앞서가거나 수치·날짜·임상 결과를 근거 없이 단정하는 일을 줄입니다.

**구현:** 답변과 근거를 비교해 `pass`, `revise`, `insufficient_evidence`로 판정합니다. 결과 미보고 등 주요 상황에는 규칙 기반 검사를 함께 적용하고, 재작성은 최대 한 번으로 제한합니다. 충분한 근거가 없다고 판단해도 일반 개념 설명까지 무조건 거부하지 않도록 질문의 성격을 나누고 복구 검색 경로를 둡니다.

**검증:** 합성 판정 13건에서 기대 분류와 13/13 일치했고, 근거를 벗어난 합성 답변 6건은 0건 통과했습니다. 단일 비교 사례의 답변 시간은 `3.19초 → 6.15초`로 늘었습니다. 이는 작은 합성 평가 결과입니다. [답변 검증 실험](docs/experiments/F3_answer_validation.md), [근거 복구 실험](docs/experiments/F9_18_tutor_evidence_recovery.md).

**화면 캡처:** 근거 부족 판정과 공식 참고자료를 표시한 답변입니다.

![근거 검증 결과와 공식 참고자료가 표시된 Tutor 답변](docs/experiments/assets/F5_5_answer_validation.png)

### 5.6 SSE 응답 및 오류 처리

**목표:** 긴 AI 작업의 진행 상태를 보여주고, 연결·검색·생성 오류가 사용자에게 드러나도록 합니다.

**구현:** FastAPI가 진행 상태, 검증을 마친 답변 조각, 참고자료, 후속 질문, 완료 또는 오류 이벤트를 SSE로 전송합니다. 검증 전 초안을 노출하지 않으므로 모델 생성 토큰을 생성 즉시 표시하는 방식은 아닙니다. 요청 취소, 유휴 시간 초과, 종료 이벤트 누락을 처리하고 재시도할 수 있는 오류를 표시합니다. 자동 재연결을 보장한다고 설명하지 않습니다.

**검증:** 합성 API를 사용한 브라우저 E2E에서 세션, SSE, 취소·오류 상태를 확인했습니다. 실제 네트워크별 장애 복구는 추가 검증이 필요합니다. [SSE 실험](docs/experiments/F6_2_sse_streaming.md), [브라우저 E2E](docs/experiments/F6_4_browser_e2e.md).

**구현:** 대화가 있으면 질문·답변을 반영해 메모 초안을 만들고, 대화가 없으면 용어 기본 정리를 제공합니다. 메모 형식은 `한 줄 개념 → 기사에서 중요한 이유 → 기억할 점 → 헷갈렸던 부분 Q&A`이며 사용자가 수정한 뒤 저장합니다. 저장된 기록에서는 질문을 눌러 답변을 펼칠 수 있습니다. 세션·기사·대화·메모는 SQLite에 보관합니다. API 프로세스는 요청 간 상태를 프로세스 메모리에만 의존하지 않으며, 세션 범위는 익명 토큰으로 확인합니다.

### 5.10 FastAPI 의존성 주입 및 모듈화

**목표:** UI, API, AI 처리, 저장소를 역할별로 분리해 테스트와 변경을 쉽게 합니다.

**구현:** Vue 3 UI와 FastAPI 백엔드를 분리하고, 기사·학습·Agent·검색·DB를 Python 모듈로 나눴습니다. FastAPI `Depends`와 그래프 생성 함수의 주입 지점을 사용해 테스트에서 실제 모델·검색·저장소 의존성을 대체할 수 있습니다. 서비스는 MSA가 아니라 단일 API 프로세스로 배포하는 모듈형 모놀리스입니다.

**검증:** API 테스트에서 의존성을 대체하고 격리된 DB·대역 모델을 사용합니다. 기존 로컬 검증 기록은 회귀 테스트 81개와 Vue 프로덕션 빌드 성공입니다(2026-10-21 기록; 이 수정 과정에서 재실행한 결과는 아닙니다).

**화면 캡처:** 이 구조는 UI에 직접 표시되지 않으므로 아키텍처 다이어그램과 테스트 기록으로 확인합니다. API/의존성 테스트 캡처가 제공되면 추가합니다.

### 5.11 비용·지연 최적화

**목표:** 불필요한 모델 호출과 기다림을 줄이면서 답변 품질을 유지할 수 있는지 평가합니다.

**구현:** 질문 경로를 나눠 필요한 검색만 수행하고, Validator 재작성은 최대 1회로 제한합니다. 독립된 학습 기록·웹 검색은 복합 경로에서 병렬 수행합니다. 별도 Planner는 추가 호출 대비 이점이 작아 기본 경로에 넣지 않았습니다.

**검증:** 라우팅 평가에서 토큰 증가는 소폭 있었고 비용 절감은 측정되지 않았습니다. Planner는 품질 이득 없이 토큰 사용이 약 46% 늘었습니다. 병렬 검색 지연 수치는 고정 지연 합성 테스트이며 실제 API 비용 절감은 미측정입니다. 따라서 구현은 비용을 고려한 호출 제한과 선택이지만, 비용 최적화 효과가 입증됐다고 주장하지 않습니다. [Query Routing 평가](docs/experiments/F8_1_query_routing.md), [Planner 평가](docs/experiments/F8_2_dynamic_planning.md), [병렬 검색 실험](docs/experiments/F8_4_parallel_sources.md).

**화면 캡처:** 비용 계측 UI는 구현되어 있지 않아 실험 결과와 ADR을 검증 자료로 제시합니다.

### 5.12 ADR 및 Observability & Eval

**목표:** 기술 선택의 근거와 성능·품질 확인 방법을 기록해 변경 결과를 재현 가능하게 합니다.

**구현:** 모듈형 모놀리스, SQLite, Validator, Query Routing, Dynamic Planning 보류, MCP, 병렬 검색 등의 선택·대안·영향을 ADR로 기록합니다. 자동화 단위·통합 테스트와 RAG·Validator·라우팅·MCP·병렬 처리별 로컬 평가 문서를 유지합니다. **LangSmith 연동, 중앙 집중 실행 추적, 서비스 운영 지표 대시보드는 구현되어 있지 않습니다.** 현재 관측·평가는 저장소 내 테스트와 실험 기록에 한정됩니다.

**검증:** README에 기재한 기존 기록은 백엔드 테스트 81개 통과, Vue 빌드 성공이며 세부 결과는 각 실험 문서에 있습니다. LangSmith 미사용 상태를 포함해 실제 구현 범위를 구분했습니다. [ADR 목록](docs/adr/), [실험 기록](docs/experiments/).

**화면 캡처:** 실행 추적 UI는 없으므로 테스트·실험 기록을 검증 자료로 제시합니다. 최종 애플리케이션 화면은 7번에 배치합니다.

| `POST` | `/api/sessions/{session_id}/articles/mark-read` | 읽은 기사 등록 및 중복·이슈 판정   | JSON      |
| `GET`  | `/api/sessions/{session_id}/articles`           | 세션에서 읽은 기사 목록            | JSON      |
| `GET`  | `/api/sessions/{session_id}/industry-issues`    | 세션별 산업 이슈 묶음 조회         | JSON      |

**인증·세션:** `/api/sessions`에서 발급받은 접근 토큰을 세션 전용 API 요청의 `Authorization` 헤더에 전달합니다. 잘못되거나 없는 세션 접근 권한은 동일한 `404` 응답으로 처리하여 세션 존재 여부 노출을 줄입니다. 익명 토큰은 정식 사용자 인증을 대체하지 않습니다.

**SSE 이벤트:** `status`(진행 단계) → `token`(검증된 답변 조각) → `sources`(참고 근거) → `recommendations`(후속 질문) → `done`(완료) 순서로 전송하며, 실패 시 `error`를 전송합니다. `token`은 **Validator 검증 후** 제공되므로 모델의 미검증 초안이 노출되지 않습니다.

**요청·응답 스키마:** 정확한 필드와 타입은 서버 실행 후 [Swagger UI](http://127.0.0.1:8000/docs) 또는 [OpenAPI JSON](http://127.0.0.1:8000/openapi.json)에서 확인할 수 있습니다. MCP는 위 HTTP API와 별도의 서버 진입점으로 제공됩니다.

### 6.2 환경 변수

루트 디렉터리에 Git으로 추적하지 않는 `.env` 파일을 작성합니다. `.env.example`을 복사해 API 키를 입력해도 됩니다.

기본 DB 경로는 `pharmamate_data/pharmamate.sqlite3`입니다. 실제 API 호출에는 제공자 요금이 발생할 수 있습니다. `.env`, 로컬 DB, 개인 학습 기록, `eval/results/`의 생성 로그는 저장소에 커밋하지 마세요.

### 6.3 Docker Compose 실행

Docker Engine이 실행 중인지 확인한 뒤 프로젝트 루트에서 진행합니다. `.env`가 없을 때 예시 파일을 복사하고 `OPENAI_API_KEY`에 실제 키를 입력합니다. 기존 `.env`가 있으면 그대로 사용합니다.

```bash
cp -n .env.example .env
docker compose up --build -d
docker compose ps
```

- 웹 화면: http://127.0.0.1:8080
- API 상태: http://127.0.0.1:8000/api/health
- API 명세: http://127.0.0.1:8000/docs
- 로그 확인: `docker compose logs -f api web`
- 종료: `docker compose down`

SQLite 학습 데이터는 `pharmamate_data` Docker 볼륨에 저장되어 컨테이너를 내려도 유지됩니다. 데이터까지 초기화하려면 `docker compose down --volumes`를 실행합니다. Compose 포트는 `.env`의 `PHARMAMATE_WEB_PORT`, `PHARMAMATE_API_PORT`로 바꿀 수 있습니다.

Compose는 API 컨테이너가 정상 상태가 된 뒤 웹 컨테이너를 시작합니다. Nginx는 `/api` 요청을 FastAPI로 전달하고, SSE 응답을 중간에 모으지 않도록 설정되어 있습니다.

#### 동일 입력 답변 비교 화면 — EVIDENCE-01

같은 가상 기사와 질문을 사용한 2.2 기준선·3.0 후보 결과를 나란히 정리했습니다. 그림의 답변은 원문 전체가 아니라 실험 기록에 적힌 핵심 응답 요약입니다.

![동일 입력 EVIDENCE-01의 PharmaMate 2.2와 3.0 답변·지연·재작성 및 RAG 지표 비교](docs/experiments/assets/F8_before_after_comparison.png)

현재 답변 복구 로직의 상한은 같은 근거에 대한 답변 수정 1회, 전체 웹 검색 2회입니다. 검색 보강으로 새 공식 근거가 확인되어야 답변을 다시 생성합니다. 이 상한은 설정값이며, 실제 사용자 요청에서의 재작성·추가 검색 빈도는 아직 계측하지 않았습니다. 위 EVIDENCE-01의 1회 재작성은 F3 시점의 단일 합성 사례 결과입니다.

**평가 설계:** 비교 대상의 변경 요소를 명시하고, 같은 합성 데이터·질문과 가능한 한 같은 모델·설정을 사용했습니다. RAG는 검색 지표(Recall@3, MRR)와 지연을, Validator는 근거 판정 결과와 응답 지연·재작성 횟수를 함께 기록했습니다. F5 행은 3.0 안에서 분리 호출과 통합 호출을 동일한 합성 입력 4건으로 비교한 별도 비용 실험입니다. 실제 사용자 데이터·장기간 운영·대규모 기사에 대한 검증은 수행하지 않았습니다. 토큰·비용이 제공되지 않은 실행은 **미측정**으로 취급합니다.

**해석상의 주의:** 검색 Recall@3 개선은 최종 답변 정확도 개선과 같지 않습니다. Validator 13/13은 모든 종류의 환각을 방지한다는 의미가 아닙니다. 실제 답변 지연 비교는 단일 사례이므로 통계적 평균으로 해석할 수 없습니다.

**근거 문서:** [F2 개인화 RAG](docs/experiments/F2_personalized_rag.md), [F3 근거 검증](docs/experiments/F3_answer_validation.md), [F5 추천 질문·비용 비교](docs/experiments/F5_dynamic_followup_questions.md). 추가 실험과 선택 기술 비교는 [`docs/experiments/`](docs/experiments/)에 있습니다.

### 8.3 기술 채택·보류의 판단 기준

- **채택:** 기능이 정상 동작하고, 목표 지표·사용성·연동 가치가 추가 지연·비용·운영 복잡도보다 유의미한 경우
- **보류:** 복잡도 또는 모델 호출 비용이 증가했으나 측정된 이점이 충분하지 않은 경우
- **구분:** MCP는 주로 표준 인터페이스와 재사용성, 병렬 실행은 지연, Validator는 근거성, RAG는 검색 품질을 각각 검증해야 함
- **모델 공정성:** Ollama와 OpenAI처럼 **모델 자체가 다른 비교**를 시스템 구조 개선 효과로 해석하지 않음

## 10. 한계점 및 향후 개선 방향

### 현재 한계

1. **기사 추출 범위:** 언론사별 HTML 변경, 유료·로그인 기사, JavaScript 동적 로딩에 따라 본문 추출이 실패하거나 부정확할 수 있습니다.
2. **근거의 신뢰성:** Validator는 제공된 근거와 답변의 일치 여부를 돕지만 출처 자체의 사실성, 모든 누락·오판을 보증하지 않습니다. 특정 임상시험의 실제 결과가 확인되지 않으면 확정 답변을 할 수 없습니다.
3. **평가 일반화:** 검색 14개 기록·20개 질의, Validator 13건 등 **소규모 합성 사례** 중심입니다. 실제 사용자 학습 효과와 장기 유지율은 미측정입니다.
4. **성능·비용:** 의미 검색의 임베딩 호출과 Validator 재작성은 지연·API 비용을 증가시킵니다. SSE는 검증 전 원시 토큰을 표시하지 않아 첫 본문 출력이 늦을 수 있습니다.
5. **운영·보안:** 로컬 SQLite와 익명 세션 토큰은 공개 다중 사용자 환경의 인증·동시성·백업·관측 요구사항을 충족하지 않습니다. 학습 메모를 외부 임베딩 API로 보내는 데이터 처리도 고려해야 합니다.
6. **도메인 종속성:** 제약·바이오 용어 규칙과 프롬프트가 코드에 남아 있어 분야만 바꾸면 즉시 동작하는 범용 Agent는 아닙니다.

### 향후 개선 방향

**장기 목표는 PharmaMate를 ‘분야별 기사 학습 Agent’의 재사용 가능한 템플릿으로 확장하는 것**입니다. 기사 추출·세션·검색·SSE·학습 메모·근거 검증은 공통 엔진으로 유지하고, 분야별 규칙은 도메인 프로필로 분리합니다.

| 도메인 프로필    | 제약·바이오 예시         | 타 분야 확장 시 변경 항목    |
| ---------------- | ------------------------ | ---------------------------- |
| 기사 분류·브리핑 | 임상·허가·기업 이슈      | 분야별 사건·기사 유형        |
| 용어 체계        | 신약·임상시험·규제       | 전문 용어 분류·제외 규칙     |
| Tutor 설명 원칙  | 기전·시험 설계·근거 구분 | 분야별 설명 수준·주의할 주장 |
| 신뢰 출처        | 규제기관·임상 등록 자료  | 분야별 공식 근거와 검색 범위 |
| 평가 데이터      | 제약 기사·질문·기대 근거 | 분야별 검증 질문·정답 출처   |

이 외에도 **실제 사용자 기반 검색·답변 평가셋 확대**, 검색 출처 재순위화, 기사별 추출 규칙 유지관리, 사용자 인증·DB 운영 개선, API 지연·비용 계측, 추천 질문의 학습 효과 평가가 필요합니다. 반도체·경제 등 타 분야로 확장할 때는 프로필 분리만으로 완료 처리하지 않고, 새 분야의 기사 추출·용어 분석·근거 검증을 별도로 회귀 테스트해야 합니다.
