# ADR-002: SQLite 기반 개인 학습 벡터 인덱스

- 상태: 채택
- 결정일: 2026-10-20
- 관련 기능: F2 Personalized RAG

## Context

PharmaMate는 이미 SQLite를 원본 저장소로 사용하고, 현재 로컬 단일 사용자 규모다. 과거 용어·메모·Q&A·기사 맥락을 의미 검색할 수 있어야 하지만, 별도 Vector DB 운영과 데이터 이중화는 이번 범위에 부담이 된다. 학습 기록 원문과 답변은 사용자 로컬 SQLite에 남아야 한다.

## Alternatives

1. 별도 Vector DB 서비스를 붙이고 SQLite의 원본 기록과 동기화한다.
2. SQLite에 임베딩 JSON을 보관하고 Python에서 cosine 유사도를 계산한다.
3. 기존 용어명·정의에 대한 단어 일치 검색만 유지한다.

## Decision

옵션 2를 채택한다. `memory_embeddings` 테이블은 원본 기록에서 파생되는 청크 인덱스이며 `chunk_id`, `owner_id`, 원본 유형·ID, `term_key`, 내용 해시, 임베딩 모델, 임베딩 JSON, 갱신 시각을 저장한다. 내용 해시와 모델명이 바뀐 청크만 다시 임베딩하고, 원본에 없는 청크는 제거한다. 검색은 임베딩 cosine 유사도와 단어 중첩 점수의 혼합 순위로 최대 3개 결과를 가져온다. OpenAI 임베딩 API를 사용할 수 없으면 기존 SQLite 단어 검색을 사용한다.

## Consequences

- 배포할 벡터 서비스 없이 기존 SQLite 백업·복구 절차를 유지한다.
- 작은 단일 사용자 인덱스에는 구현이 간단하지만, 기록이 커지면 매 요청 Python cosine scan 비용이 늘어난다. 규모가 커질 때 전용 Vector DB/SQLite 벡터 확장을 다시 평가한다.
- 신규·변경 기록과 질문 텍스트가 임베딩 처리를 위해 설정된 OpenAI API로 전송되며 API 비용과 외부 데이터 처리 의존성이 생긴다.
- 현재 앱은 `local` 소유자만 검색한다. 사용자·세션별 격리는 F7의 소유권 스키마와 함께 완성해야 한다.
- 임베딩 실패 시 단어 검색으로 복구되지만, 유사 표현 검색 품질은 낮아질 수 있다.

## Evidence

합성 학습 기록 14개와 질의 20개 실험에서 기존 단어 검색은 Recall@3 0.950, MRR 0.925였고, 의미 혼합 검색은 Recall@3 1.000, MRR 0.942였다. 후보 검색 지연은 p50 0.160초, p95 0.184초였으며 기존 단어 검색은 측정 분해능에서 0초로 나타났다. 조건과 한계는 [F2 실험 보고서](../experiments/F2_personalized_rag.md)에 기록했다.
