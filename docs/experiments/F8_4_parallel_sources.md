# F8.4 개인 기록·웹 검색 병렬 실행 실험

## 질문과 조건

복합 질문은 개인 학습 기록 검색과 최신 웹 검색을 모두 기다린 뒤 답변을 만든다. 두 입력 작업은 서로 독립적이므로 순차 실행을 병렬 실행으로 바꿨을 때 결과가 유지되고 지연이 줄어드는지 확인했다.

- 두 합성 source 함수가 각각 고정 80 ms I/O 대기 후 같은 결과를 반환
- 순차/병렬 각 30회, 출력 결과와 source 성공 여부 확인
- 후보는 재사용하는 `ThreadPoolExecutor`의 두 worker로 두 source를 시작. 전역 최대 worker 수는 8
- 별도 LangGraph 테스트에서 barrier를 이용해 memory/web 함수가 동시에 실행되고 둘 다 답변 상태에 도달하는지 확인
- 재현: `python eval/run_parallel_sources_experiment.py`

## 결과

| 측정값 | 순차 실행 | 병렬 실행 |
|---|---:|---:|
| p50 작업 지연 | 166.60 ms | 84.60 ms |
| source 결과 모두 성공 | 30/30 | 30/30 |
| 두 결과의 일치 | 예 | 예 |
| 한 요청 안 최대 동시 작업 | 1 | 2 |

고정 지연 fixture에서 p50은 49.2% 줄었다. 모델 호출이나 토큰을 추가하지 않는다. 병렬 작업의 결과는 순차 실행과 같았다.

## 결정과 한계

`memory_web` 경로에만 병렬 실행을 채택했다. 앱에 Tavily 검색 클라이언트가 없을 때는 즉시 반환하는 웹 오류 메시지와 memory 검색을 병렬화하지 않고 기존 순차 경로를 사용한다. 메모리 검색 또는 웹 검색 중 하나가 실패하는 기존 오류 의미는 유지한다.

80 ms 고정 대기는 네트워크 기반 호출의 겹침 효과를 재현하는 fixture이지, OpenAI embedding 또는 Tavily의 실측값이 아니다. 실제 종단 간 API p50/p95, 사용자 트래픽에서의 자원 사용량은 미측정이다. 전역 8 worker 상한은 요청 동시성이 커질 때 추가 부하를 제한하지만, 포화 지점은 별도 부하 테스트가 필요하다.
